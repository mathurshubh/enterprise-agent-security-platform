## Overview

Version **0.18.0** is the first published release since `v0.15.0`. It establishes the platform's durable security-state plane, moves tool execution out of the gateway process entirely, and closes the tool- and audit-identity gaps that let one identifier stand for several different facts.

### Why the version jumps from v0.15.0 to v0.18.0

`v0.16.0` was *proposed* as a documentation and baseline synchronization checkpoint and was never ratified, tagged or published. `v0.17`, `v0.17.1` and `v0.17.2` were **development-cycle labels**, not release boundaries — the work they named was merged as a single pull request. Git tags are this repository's release authority, and no tag was ever created for any of them.

The gap is therefore deliberate. Publishing `v0.16.0` now would contradict the record, and manufacturing historical `v0.16`/`v0.17.x` releases would assert publications that never happened. `v0.18.0` is the accumulated state from `v0.15.0` to the current baseline.

## Security guarantees established or changed

These are the properties a reader should take from this release, independent of any individual change:

- **Security state survives process restart.** Session sequencing, detection horizons, enforcement epochs and execution grants are backed by a relational control plane with compare-and-set state progression, rather than existing only in process memory.
- **Tool execution never runs in the gateway process.** Authorized invocations execute exclusively across a process sandbox boundary, with no in-process fallback on sandbox absence or error.
- **An authorization decision binds to one concrete operation.** A grant authorizes exactly the tool, version, resource and parameters that were evaluated — not merely the tool family that was named.
- **Execution identity is never inferred.** The concrete implementation that runs is declared at registration and carried on the grant, the sandbox invocation and the receipt. Nothing derives it from a tool identifier.
- **Grant revocation is asymmetric, and the asymmetry is bounded.** Agent containment revokes outstanding grants immediately; other governance changes take effect for grants issued afterwards, within a 30-second policy ceiling that is refused rather than silently widened.
- **Audit evidence cannot be made unrecordable by control-plane state.** A request may be denied at a trust boundary — including for naming a tool that does not exist — and its denial evidence is still durably recorded.
- **Requested and resolved identity are distinct facts.** Audit records what a request named *and* what the pipeline resolved, so a record cannot be reinterpreted through later registry state.
- **Management and runtime planes are separately authorized.** Authority to manage an agent is never authority to act as one.

## Highlights

### 1. Durable state and repository architecture

Established the durable security-state plane (Plane 3) behind repository protocol interfaces: in-memory and SQL adapters held to a single shared contract suite, services converted to dependency-injected repositories, and a durable enforcement-state contract with monotonic epoch progression. The enforcement baseline was separated into one column per monotonic sequence namespace after a single watermark was found serving two counters with independent allocators.

### 2. Runtime execution isolation and execution evidence

Tool execution moved into an isolated child process with immutable, signed capability bindings, process-level filesystem and network guards, and no in-process fallback. Execution provenance is derived from the verified grant rather than caller-supplied context. Execution evidence is recorded on the production path with grant-derived correlation, bounded terminal retention, a non-silent integrity signal, and startup reconciliation completed before readiness.

### 3. Management-plane authorization and agent lifecycle

Every published route belongs to a plane with a declared role set, evaluated at the router mount before any resource lookup. Sessions are bound to their owning agent, agent suspension withdraws outstanding execution authority, and reinstatement is an authorized, attributed administrative action rather than a runtime path.

### 4. Behavioral telemetry, risk and finding identity

Added the behavioral telemetry architecture, materialized risk projection with enforcement epochs, and finding identity derived from the occurrence rather than the aggregation scope. Authorization decisions emit structured evidence, and audit events correlate to their originating session.

### 5. Tool and audit identity integrity

Tool identity became versioned in the domain, then durable: `tool_families` alongside `tools(tool_id, version)`, with version-scoped enablement and family-scoped authorization kept distinct. Session events and execution grants reference the concrete version, each with the referential strategy its nullability requires. Audit events record requested and resolved identity as separate facts, and audit storage deliberately holds no reference to the tool registry.

### 6. Architecture and security documentation

Two contracts that governed durable behaviour were recorded as decisions: the tool catalog contract (ADR-033) and the audit identity contract (ADR-034). The threat model gained invariants covering audit-recording independence and record interpretability, and its audit trust boundary is now documented as one-directional.

### 7. Security hardening and validation

A remediation pass closed defects in capability digest coverage, sandbox resource controls, runner resolution, packaged-implementation declaration, receipt execution identity, and refusal finalization. Two dependency advisories were remediated in dedicated changes. Security-relevant behaviour is covered by `security_invariant` and `security_regression` suites, and changes in this stream were validated by mutation testing against the specific property each change claimed.

## Not included in this release

Recorded here so the release is not read as claiming more than it delivers:

- The tool catalog API projection described by ADR-033 is **not implemented**; the contract is accepted and the durable model it reads from exists.
- The audit reconciliation detection described by ADR-034 §2.5 is **not implemented**.
- Execution receipt persistence, capability-profile persistence and capability applicability are **not implemented**; the evidence durability boundary is an open architectural decision.
- Production repositories remain **in-memory**. The SQL adapters are complete and contract-tested, but the production wiring switch is a separate decision.
- Governance-state snapshots in audit records and operator attribution semantics remain **open decisions**.
